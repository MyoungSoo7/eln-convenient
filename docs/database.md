## 2. PostgreSQL

### 현재 설정

```
max_connections=30
shared_buffers=256MB
effective_cache_size=512MB
work_mem=8MB
maintenance_work_mem=128MB
wal_buffers=4MB
```

- 서비스 8개 × `connection_limit=3` = 24 커넥션 사용 (잔여 6)

### 행 증가 내역 (사용자 1명/월)

| 테이블 | 월간 행 |
|--------|---------|
| AuditLog | ~200 |
| NoteRevision | ~100 |
| NoteStatusHistory | ~50 |
| SearchHistory | ~50 |
| Note | ~25 |
| 기타 (File, Signature, Booking 등) | ~25 |
| **합계** | **~450** |

### 규모별 산정

| 항목 | 10명 | 50명 | 200명 | 500명 |
|------|------|------|-------|-------|
| 월간 신규 행 | ~4,500 | ~22,500 | ~90,000 | ~225,000 |
| 월간 DB 증가량 | ~5MB | ~25MB | ~100MB | ~250MB |
| 1년 누적 | ~60MB | ~300MB | ~1.2GB | ~3GB |
| 동시 쿼리 (피크) | ~3 | ~10 | ~30 | ~60+ |
| 필요 커넥션 | 24 (현재) | 24 (현재) | **40+** | **60+** |

### 스케일업 기준

| 규모 | max_connections | shared_buffers | work_mem |
|------|----------------|----------------|----------|
| ~50명 | 30 (현재) | 256MB (현재) | 8MB (현재) |
| ~200명 | 60 | 512MB | 16MB |
| ~500명 | 100 | 1GB | 32MB |

**병목**: `max_connections=30`에서 서비스 24개 사용 중. 50명까지는 현재 설정으로 충분. 200명 이상이면 커넥션 풀 확대 필요.

## 3. Redis

### 현재 설정

```
maxmemory=128MB
maxmemory-policy=allkeys-lru
save "300 1"
databases=4
timeout=300
```

### 메모리 사용 내역

| 용도 | 키 패턴 | TTL | 비고 |
|------|---------|-----|------|
| 토큰 블랙리스트 | `blacklist:${token}` | 8h | 모든 인증 요청 |
| 사용자 무효화 | `blacklist:user:${userId}` | 8h | 역할 변경 시 |
| 검색 캐시 | `cache:search:${sha256}` | 3분 | 모든 검색 쿼리 |
| 대시보드 캐시 | `cache:dashboard:*` | 가변 | 사용자별 |
| 카테고리 캐시 | `category:${orgId}` | 가변 | 조직별 |
| Stream (이벤트) | `labnote:events`, `audit:events` | MAXLEN 1000~10000 | 이벤트 동기화 |
| BullMQ 큐 | `labnote-export`, `labnote-notification` | 작업 완료 시 정리 | PDF/알림 |
| Pub/Sub | `labnote:collab`, `labnote:note-status` | 메모리 무시 | 실시간 협업 |

### 규모별 산정

| 항목 | 10명 | 50명 | 200명 | 500명 |
|------|------|------|-------|-------|
| 토큰 블랙리스트 | ~1KB | ~5KB | ~20KB | ~50KB |
| 검색 캐시 (정상상태) | ~500KB | ~2MB | ~8MB | ~20MB |
| 대시보드 캐시 | ~50KB | ~250KB | ~1MB | ~2.5MB |
| Stream 메시지 | ~1MB | ~5MB | ~10MB (cap) | ~10MB (cap) |
| BullMQ 큐 | ~500KB | ~2MB | ~5MB | ~10MB |
| **합계 (피크)** | **~3MB** | **~10MB** | **~25MB** | **~45MB** |

### 스케일업 기준

| 규모 | maxmemory | 비고 |
|------|-----------|------|
| ~200명 | 128MB (현재) | 충분, LRU가 보호 |
| ~500명 | 256MB | 캐시 히트율 유지 |
| ~1000명 | 512MB | Stream + BullMQ 여유 확보 |

**병목**: 128MB + LRU 정책으로 500명까지 운영 가능. 캐시 히트율 저하 시 maxmemory 증가.

## 4. MinIO (S3 호환 오브젝트 스토리지)

### 현재 설정

- 리소스 제한 없음, 디스크 바운드
- 버킷: `labnote-files` (영구), `labnote-exports` (임시 24~48h)
- Presigned URL: 다운로드 1h, 업로드 15min

### 규모별 산정

| 항목 | 10명 | 50명 | 200명 | 500명 |
|------|------|------|-------|-------|
| 월간 업로드 | 200MB | 1GB | 4GB | 10GB |
| 월간 Export (임시) | ~50MB | ~250MB | ~1GB | ~2.5GB |
| 1년 누적 (파일) | 2.4GB | 12GB | 48GB | 120GB |
| Presigned URL 동시 | ~2 | ~10 | ~40 | ~100 |

Export는 cleanup job으로 24~48시간 후 자동 삭제.

### 스케일업 기준

| 규모 | 디스크 | 네트워크 |
|------|--------|----------|
| ~50명 | 100GB SSD | 100Mbps |
| ~200명 | 250GB SSD | 500Mbps |
| ~500명 | 500GB SSD+ | 1Gbps |

**병목**: 디스크 I/O + 용량. 500명 기준 일반 SSD 500GB면 4년 운영 가능.

## 5. OpenSearch

### 현재 설정

```
JVM Heap: -Xms256m -Xmx256m
단일 노드, 샤드 1, 레플리카 0
플러그인: analysis-nori (한국어)
인덱스: lab_search_v1 (별칭: lab_search)
```

### 문서 스키마

| 필드 | 타입 | 분석기 | 부스트 |
|------|------|--------|--------|
| title | text | korean/korean_search | 4x |
| tags | text | korean/korean_search | 3x |
| summary | text | korean/korean_search | 2x |
| content | text | korean/korean_search | 1x |
| orgId, docId, domainType, visibility | keyword | - | - |

### 규모별 산정

| 항목 | 10명 | 50명 | 200명 | 500명 |
|------|------|------|-------|-------|
| 월간 인덱싱 문서 | 250건 | 1,250건 | 5,000건 | 12,500건 |
| 인덱스 크기/월 | ~750KB | ~3.7MB | ~15MB | ~37MB |
| 1년 누적 인덱스 | ~9MB | ~45MB | ~180MB | ~450MB |
| 월간 검색 쿼리 | 600회 | 3,000회 | 12,000회 | 30,000회 |
| 피크 QPS | ~0.5 | ~2 | ~8 | ~20 |

문서당 평균 ~3KB (title + content + Korean tokenization overhead).

### 스케일업 기준

| 규모 | JVM Heap | 샤드 | 레플리카 |
|------|----------|------|---------|
| ~50명 | 256MB (현재) | 1 | 0 |
| ~200명 | 512MB | 1 | 0 |
| ~500명 | 1GB | 2 | 1 |

**병목**: JVM 256MB는 인덱스 ~200MB 초과 시 GC 압박. 200명까지 현재 설정으로 1년 운영 가능.

## 6. Qdrant (벡터 DB)

### 현재 설정

```
리소스 제한 없음 (RAM 의존)
컬렉션: labnote_docs_${EMBEDDING_DIM}
벡터 차원: 1536 (OpenAI) 또는 1024 (bge-m3)
거리 함수: Cosine
청크: 800자, 100자 오버랩
```

### 규모별 산정

| 항목 | 10명 | 50명 | 200명 | 500명 |
|------|------|------|-------|-------|
| 월간 벡터 | ~1,500 | ~7,500 | ~30,000 | ~75,000 |
| 벡터 저장/월 | ~9MB | ~45MB | ~180MB | ~450MB |
| 1년 누적 | ~108MB | ~540MB | ~2.2GB | ~5.4GB |
| 월간 RAG 쿼리 | 150회 | 750회 | 3,000회 | 7,500회 |
| 피크 QPS | ~0.1 | ~0.5 | ~2 | ~5 |

벡터: 1536차원 x 4바이트 = 6KB/벡터. 문서당 ~6청크 = ~36KB/문서.

### 스케일업 기준

| 규모 | 필요 RAM (1년) | 디스크 |
|------|---------------|--------|
| ~50명 | ~1GB | 2GB |
| ~200명 | ~3GB | 5GB |
| ~500명 | ~6GB | 10GB |

**병목**: Qdrant는 벡터를 RAM에 상주시켜 검색. 벡터 100만개 ≈ 6GB RAM 필요.

## 7. 종합 요약

### 컴포넌트별 한계

| 컴포넌트 | 현재 설정 | 한계 사용자 수 | 첫 번째 병목 | 스케일업 시점 |
|----------|----------|---------------|-------------|-------------|
| **PostgreSQL** | 30 conn, 256MB buf | **~50명** | 커넥션 풀 (30개 중 24 사용) | 동시 접속 50명 초과 시 |
| **Redis** | 128MB, LRU | **~500명** | 메모리 (LRU가 보호) | 캐시 미스율 증가 시 |
| **MinIO** | 무제한 | **디스크 한도** | 디스크 I/O + 용량 | 월 10GB+ 업로드 시 |
| **OpenSearch** | 256MB JVM | **~200명 (1년)** | JVM 힙 vs 인덱스 크기 | 인덱스 200MB 초과 시 |
| **Qdrant** | 무제한 | **RAM 의존** | 벡터 RAM 상주 | 벡터 50만개 초과 시 |

### 권장 규모별 프로파일

|  | S (10~30명) | M (50~100명) | L (200~500명) |
|---|---|---|---|
| PG max_connections | 30 | 50 | 100 |
| PG shared_buffers | 256MB | 512MB | 1GB |
| Redis maxmemory | 128MB | 128MB | 256MB |
| OpenSearch JVM | 256MB | 512MB | 1GB |
| Qdrant RAM | 1GB | 2GB | 8GB |
| MinIO 디스크 | 50GB | 100GB | 500GB |
| **총 서버 RAM** | **4GB** | **8GB** | **16GB+** |

> 현재 설정은 **S 프로파일 (10~30명)** 에 최적화되어 있다.
> 첫 번째 병목은 PostgreSQL 커넥션 풀(30개)이 될 가능성이 높다.
